# owbridge - a USART/SPI/soft-I2C to 1-Wire bridge on the STM32F030F4P6

Firmware for a microcontroller gateway that lets a host drive a 1-Wire bus.
Every microsecond-scale 1-Wire timing is generated by TIM1 and DMA through the
[`stm32-async-1wire`](https://github.com/a5021/stm32-async-1wire) library
(v3.1.3); the CPU only polls completion flags. **The firmware is fully polled:
no NVIC interrupts are enabled.**

New to the protocol? [`docs/how-it-works.md`](docs/how-it-works.md) is an
illustrated tour with captured frames, a queued command, a raw DS18B20
conversation and an hour of load-test output.

## Host interface selection

The host-facing interface is chosen at compile time, one per firmware image:

```bash
cmake -DHOST_IF=UART ...   # USART1
cmake -DHOST_IF=SPI  ...   # SPI1 slave
cmake -DHOST_IF=I2C  ...   # software I2C slave
```

Only the selected `host_*.c` is compiled, so flash and RAM stay small and the
main loop only services one host interface plus the 1-Wire bus.

## Hardware platform

STM32F030F4P6 in a TSSOP-20 package. The datasheet documents 16 KB of flash,
but the die carries **32 KB** (like the F6P6); the upper 16 KB are used by the
linker script. RAM is 4 KB.

Pins common to every variant:

| Pin | Function | Notes |
|-----|----------|-------|
| PA10 | 1-Wire DQ | TIM1_CH3, AF2, open-drain (owned by the library) |
| PA9 | Strong pull-up switch | gate-driver input, active-high, push-pull |
| PA0 / PA1 | Status / error LED | push-pull |
| PB1 / PF0 | Config jumpers 0 / 1 | input with pull-up |
| PF1 | Spare | input with pull-up |
| PA13/PA14 | SWD | programming |

Host-interface pins:

| Variant | Pins |
|---------|------|
| UART | PA2 = USART1 TX, PA3 = USART1 RX |
| SPI | PA4 = NSS (GPIO CS), PA5 = SCK, PA6 = MISO, PA7 = MOSI |
| I2C | PA4 = SCL (input, pull-up), PA5 = SDA (open-drain) |

1-Wire power: 3.3 V with a 4.7 kOhm pull-up (externally powered devices) or
2.2 kOhm (parasite power, with PA9 driving the strong-pull-up switch, e.g. a
P-MOSFET through its gate driver).

## Building

```bash
cmake -S . -B build \
    -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi-gcc.cmake \
    -DHOST_IF=UART
cmake --build build -j
```

The first configure fetches `stm32-async-1wire` v3.1.3 and the pinned CMSIS
repositories from GitHub into `build/_deps/`. No dependencies are vendored in
the repository.

Output: `build/owbridge.elf`, `build/owbridge.bin`, `build/owbridge.hex`.

Flashing:

```bash
st-flash write build/owbridge.bin 0x08000000
# or
openocd -f interface/stlink.cfg -f target/stm32f0x.cfg \
    -c "program build/owbridge.elf verify reset exit"
```

## Transport details

- **UART**: TX via DMA1 channel 2, RX via DMA1 channel 5 in circular mode
  (remapped from the default channel 3, which the 1-Wire feed owns, through
  `SYSCFG_CFGR1.USART1RX_DMA_RMP`). The main loop polls the DMA state, drains
  up to 32 bytes per call from a 512-byte ring, and drops a half-received
  frame or AT line after 100 ms of silence. Without interrupts there is no
  way to count ring overwrites; the 512-byte ring covers the longest blocking
  path (`CONFIG_SET`, about 23 ms) with a wide margin, and the frame CRC plus
  the gap timeout resynchronise the decoder if the host ever overruns it.
- **SPI**: polled FIFO handling in the main loop: `DR` is accessed byte-wise,
  up to four bytes are drained/filled per call, both FIFOs are reset at each
  phase boundary, and a loss-of-CS response phase returns to command mode
  after 100 ms. DMA is not possible: SPI1_RX is DMA1 channel 2 and SPI1_TX is
  DMA1 channel 3, which the 1-Wire engine owns.
- **I2C**: software slave, polled SCL/SDA edges in the main loop. No EXTI, no
  DMA (GPIO edges cannot trigger DMA). During an I2C transaction the 1-Wire
  poll is deferred (with a 50 ms no-edge safety valve), so its encode/decode
  cannot drop SCL edges at 100 kHz; the 1-Wire timing is hardware-generated, so
  only the state machine is delayed. A read transfers the response straight from
  the bridge's latched buffer; there is no `memcpy` in the SCL edge handler,
  because a copy of up to 163 bytes would outlast the 5 us low phase of a
  100 kHz clock. The dispatcher is a 256-entry table indexed by the command
  byte, commands are copied straight into the bus slot, and the hot copies are
  inline 32-bit moves (`fast_copy()`), not the byte-wise libc `memcpy`.

### I2C timing margin

The poll rate was measured with the one-off TIM3 profiler
(`-DOWBRIDGE_PROFILE=ON`, results read over SWD) on the 9-device bench, I2C
build at `-O2`:

| Metric | min | max | average |
|--------|-----|-----|---------|
| `host_i2c_soft_poll()` | 0 us | 1 us | 0.90 us |
| `bridge_poll()` | 1 us | 2 us | 1.17 us |
| main loop | 4 us | 5 us | 4.09 us |

These numbers include the profiler's two TIM3 reads and volatile bookkeeping
(about 1.5-2 us per iteration); the production loop is therefore about 2-3 us.
While an I2C transaction is active `bridge_poll()` is skipped, so the busy
loop is shorter still. The SCL half-period is 5 us at 100 kHz, but the CH341A
actually produces about 115 kHz (4.3 us), so the margin is small; 400 kHz
(1.25 us) does not work.

**The 1-2 us `bridge_poll()` figure is the idle case.** While a long command
is running, the first `bridge_poll()` after STOP (or the STOP handler itself,
for `OW_WRITE_BYTES`) can block the polled I2C sampler. Measured with the
extended profiler on the 9-device bench, final I2C build at `-O2`, host
traffic at 20 kHz (the instrumented loop is too slow for 100 kHz; the CPU cost
is independent of SCL rate):

| Blocking path | Measured max |
|---------------|--------------|
| idle `bridge_poll()` | 3 us |
| `bridge_poll()` during `OW_SEARCH` / `TEMP_READ_ALL` | 45 us |
| `bridge_poll()` during `EEPROM_WRITE` (DS2431 read-back) | 89 us |
| `bridge_submit()` inside STOP, `OW_WRITE_BYTES` 32 B | 93 us |
| `bridge_submit()` other long commands | 15-19 us |
| `config_set()` inside `bridge_poll()` (`CONFIG_SET`) | 23.3 ms |

During those windows the slave does not sample SCL, so a START/clock burst
that arrives earlier is missed. This is the mechanism behind the NACKs on
`TEMP_READ_ALL`, `OW_SEARCH` and the write commands, not an adapter defect.
A focused probe on the same bench (30 searches, 40 read-alls, 40 32-byte
writes and 10 EEPROM writes) saw **3 827 retries at 100 kHz and 0 at 20 kHz**;
every command still completed with `OK`.

Host contract while a long command is `BUSY`: treat a NACK / all-`FF` read as
"not ready" and retry; the demo and the harnesses do exactly that. A pause
between polls does *not* remove the misses: while `BUSY` the firmware calls
`bridge_poll()` back-to-back, so a host START lands inside a step with
roughly the same probability no matter how long it waited. On a 5 s scan
cadence at 100 kHz, 20 cycles produced 149 NACKs per cycle with back-to-back
polls and 91 with a 250 us gap, about 7% of the BUSY polls in both cases: the
gap halves the number of polls, not the loss rate. At 20 kHz the same cadence
measured zero. `CONFIG_SET` is different: it blocks for about 23 ms, so the
host must retry across it (the demo's 10 s timeout covers this). Instant
commands are built inside the STOP handler too. The slowest one,
`STATS_GET`, used to outlast the adapter's 15 us turnaround (it reloaded the
response pointer per byte and divided the uptime by 1000); it now writes
32-bit words and takes its uptime from a tick counter, so the chained read is
served — 0 of 300 reads NACKed at the same turnaround. A host whose
turnaround is shorter than the handler still needs the retry rule.

The per-loop edge bookkeeping for the 50 ms valve is gated to one check per
millisecond. An earlier version that read the edge counter on every busy-loop
iteration was itself enough to break 100 kHz on the production build; the
measured margin is that thin.

The 50 ms safety valve now requires **no SCL/SDA edges for 50 ms**, not merely
a transaction longer than 50 ms. A 163-byte frame at 20 kHz lasts about 74 ms
but keeps clocking, so it is never interrupted; the valve only releases a
wedged or held bus. 100 kHz remains the validated rate.

### I2C host turnaround

The STOP handler is short enough to survive the CH341A's ~15 us
STOP-to-START turnaround for instant commands: version, cached queries,
config and stats are completed inside `bridge_submit()` before the handler
returns, so the read that follows immediately sees the final response. Long
1-Wire commands start their engine at STOP and latch `BUSY`; the first
main-loop poll after STOP (up to 45-89 us) or the STOP handler itself (up to
93 us for `OW_WRITE_BYTES`) can outlast the 15 us turnaround, so a chained
read address may be NACKed and must be retried (see the timing margin above).
Once the host is polling, the response arrives as usual.

Measured worst case for an instant command on the 9-device bench: about 10 us
from STOP detection to the latched response. No host-side gap is required:
`gap = 0` on the CH341A works for `FIRMWARE_VER`, `OW_GET_COUNT`,
`OW_GET_STATUS`, `OW_GET_DEVICES` (with a populated cache), `STATS_GET` and
`CONFIG_GET`. Details: [`docs/i2c-timing.md`](docs/i2c-timing.md).

### I2C repeated START is not supported

The bridge is a polled I2C slave: a command is submitted from the STOP
handler, and the response is only ready after the main loop has run. A
repeated START (write frame followed by START instead of STOP, typically to
read with a chained transaction) is therefore **not a supported pattern**.
The address phase that follows it is NACKed, and the bridge does not treat
the preceding write as a command. Use write → STOP → short gap → read
instead, which is what `tools/owbridge_demo.py` and the CH341A adapter do.
At 100 kHz the STOP-to-read turnaround fits the slave's decoder; a master
that cannot insert a STOP must expect NACKs and retry.

## Protocol

### Binary frame (UART and SPI)

```
Command:  AA 55 [cmd][len][data...] [crc8]      (UART)
          5A A5 [status][cmd][len][data...] [crc8] (response)
```

The SPI transport uses the same `[cmd][len][data...]` /
`[status][cmd][len][data...]` frame without the `AA 55` / `5A A5` header,
inside two CS-framed phases:

1. CS low: the master sends `[cmd][len][data...]`.
2. CS high: the bridge starts the command.
3. CS low: the master clocks dummy bytes; the slave returns
   `[status][cmd][len][data...]`.

The software I2C slave uses the same bare frame: a write transaction delivers
`[cmd][len][data...]`, a read transaction returns
`[status][cmd][len][data...]`.

`crc8` is the Dallas/Maxim CRC-8 (polynomial 0x8C).

### Transport integrity

Only UART frames carry a checksum. The SPI and software-I2C frames have none:
they rely on CS / START-STOP framing, the 7-bit address ACK (I2C only), and the
per-command length and argument checks in the `br_cmd_desc_t` table.

| Transport | Framing | Wire checksum | Undetected by the transport |
|-----------|---------|---------------|-----------------------------|
| UART | `AA 55` header, length | CRC-8 over `cmd`..`data` (both directions) | only patterns beyond CRC-8 (all single-bit and bursts <= 8 bits are caught) |
| SPI | two CS-framed phases | none | any bit flip that keeps the length plausible |
| I2C | START/STOP, 7-bit address + ACK | none | any bit flip that keeps the length plausible |

Commands whose payload carries its own end-to-end check are still protected on
SPI/I2C: a ROM is checked with the Dallas CRC-8, a DS2431 scratchpad read with
CRC-16, and a configuration block with CRC-32. A corrupted length, unknown
command or invalid argument is rejected with `PARAM_ERROR` / `INVALID_CMD`.
For transport-level integrity on SPI/I2C, wrap the frame in an application
checksum; adding CRC-8 to those frames would be a protocol v2 change.

### Destructive commands

Both commands that can leave the device in a bad state verify the complete
payload before the irreversible step:

- **`CONFIG_SET`** (0x51) checks the `OWBR` magic, the version, every field
  range and the CRC-32 over the first 36 bytes *before* the flash page is
  erased. A checksum mismatch returns `CRC_ERROR`; a bad header or field
  returns `PARAM_ERROR`. The page is never written with a corrupted
  `i2c_addr`, so the I2C build cannot be bricked by a bad frame. Previously
  the firmware recomputed the CRC instead of checking it.
- **`EEPROM_WRITE`** (0x31) uses the DS2431 driver's verification: the
  scratchpad CRC-16, the TA/ES echo, the PF bit and the read-back payload are
  all checked. A failure aborts **before** Copy Scratchpad, returning
  `CRC_ERROR` (a Write Scratchpad failure returns `BUS_ERROR`), so corrupted
  data is never programmed. A rejected write leaves the page unchanged.

### AT commands (UART, for debugging)

| Command | Response |
|---------|----------|
| `AT` | `OK` |
| `AT+VER` | `owbridge 1.6.0 (lib 3.1.3)` |
| `AT+OWRST` | `OK` / `NO DEVICE` |
| `AT+OWSRCH` | `COUNT <n>` |
| `AT+OWCNT` | `COUNT <n>` |
| `AT+TEMP` | `TEMP <t1> <t2> ...` |
| `AT+STAT` | `STAT resets=<n> no_presence=<n>` |
| `AT+DEVS` | `DEVS <rom> <rom> ...` |

AT and binary share one latched response slot: do not send binary frames while
an AT command is `BUSY`, or the reply will be rendered in the wrong format
(and vice versa). `AT+DEVS` prints at most 20 ROMs, the same batch limit as
`OW_GET_DEVICES`; use the binary command with `offset` for a larger cache.

### Status codes

| Code | Name | Meaning |
|------|------|---------|
| 0x00 | OK | success |
| 0x01 | BUSY | command in progress; poll again |
| 0x02 | NO_DEVICE | no presence pulse |
| 0x03 | CRC_ERROR | checksum mismatch |
| 0x04 | BUS_SHORT | reserved; never returned (no current sensor) |
| 0x05 | TIMEOUT | operation timed out |
| 0x06 | INVALID_CMD | unknown command |
| 0x07 | PARAM_ERROR | invalid parameters (payload length or argument) |
| 0x08 | BUS_ERROR | generic bus failure |
| 0x09 | NOT_SUPPORTED | feature not supported |
| 0x0A | QUEUE_FULL | reserved; never returned since 1.3.0 |
| 0x0B | ABORTED | operation aborted |

Asynchronous commands (search, conversion, EEPROM write) first return `BUSY`;
the host keeps polling the response until it becomes `OK` or an error.

Both queue slots can be occupied by a running command and its successors. A
frame that arrives when they are full is **dropped without a response** and
counted in `queue_drop` (`STATS_GET`); it does not overwrite the in-flight
command's response. The host sees only its own timeout, so a client that
pipelines more than two commands must keep a timeout for the dropped one.
`QUEUE_FULL` (0x0A) stays in the enum for compatibility but is not emitted.

## Commands

### Raw 1-Wire

| Code | Command | Parameters | Response |
|------|---------|------------|----------|
| 0x01 | `OW_RESET` | - | `present`, `short` |
| 0x02 | `OW_WRITE_BYTE` | `data[1]` | - |
| 0x03 | `OW_READ_BYTE` | - | `data[1]` |
| 0x04 | `OW_WRITE_BYTES` | `data[1..32]` | - |
| 0x05 | `OW_READ_BYTES` | `n` (data[0], 1..32) | `data[n]` |
| 0x06 | `OW_MATCH_ROM` | `rom[8]` + payload (0..32) | `present` |
| 0x07 | `OW_SKIP_ROM` | payload (1..32) | `present` |
| 0x08 | `OW_READ_ROM` | - | `rom[8]`, `present` |
| 0x09 | `OW_SEARCH` | `cmd`, `family`, `max` | `count` |
| 0x0A | `OW_SEARCH_ALM` | `max` | `count` |
| 0x0B | `OW_SET_PULLUP` | `on/off` | - |
| 0x0C | `OW_SET_POWER` | `parasite/ext` | - |
| 0x0D | `OW_GET_STATUS` | - | `flags`, `count` |
| 0x0E | `OW_GET_DEVICES` | `offset`, `count` | `rom[8] x n` |
| 0x0F | `OW_GET_COUNT` | - | `count` |
| 0x10 | `OW_CLEAR_CACHE` | - | - |
| 0x11 | `OW_ABORT` | - | - |

`OW_ABORT` cannot interrupt the library's in-flight hardware operation: it
discards commands already queued behind it and returns `ABORTED` once the bus
is free. `OW_READ_BYTES` accepts at most 32 bytes per call (`n` in `data[0]`).

`OW_SEARCH` accepts only the two 1-Wire search opcodes: `0xF0` (Search ROM) and
`0xEC` (Alarm Search). Any other `cmd` byte is rejected with `PARAM_ERROR`
before the bus is touched, and the previous cache is left intact. Omitting the
byte defaults to `0xF0`.

The `short` byte in `OW_RESET` and the `BUS_SHORT` status are reserved: this
board has no bus-current sensor, so a short cannot be detected. `short` is
always 0 and `BUS_SHORT` (0x04) is never returned.

`OW_GET_STATUS.flags` bits:

| Bit | Name | Meaning |
|-----|------|---------|
| 0 | `BUSY` | a command is in flight |
| 1 | `CACHE_TRUNCATED` | the last search saw more devices than the cache holds |
| 3 | `PARASITE` | the DS18B20 driver is in parasite mode |

`CACHE_TRUNCATED` is set only after a completed `OW_SEARCH` / `OW_SEARCH_ALM`
and is cleared by the next search or `OW_CLEAR_CACHE`. The search collects at
most the requested `max` ROMs (capped at the compile-time cache size) but
walks one device further, so the host can tell "exactly N" from "more than N".
`OW_GET_DEVICES` returns at most 20 ROMs per response (`160 / 8`); larger
caches are read in pages with `offset` and `count`, and `AT+DEVS` prints the
first 20.

`OW_MATCH_ROM`, `OW_SKIP_ROM` and `OW_READ_ROM` append a `present` byte taken
from the reset that precedes the command. It means **at least one device
answered the reset pulse** — it is not proof that the addressed ROM exists,
because MATCH ROM and SKIP ROM are write-only and a non-matching device sends
no response. The command still answers `BR_OK` when the bus is empty; the flag
tells the host whether the bus had any device at all. `OW_READ_ROM` keeps the
ROM in the first eight bytes and puts the flag at index 8. A missing bus also
increments `read_fail` in `STATS_GET`. Firmware before 1.2.0 returned no flag
(and `OW_READ_ROM` had a length of 8). Use `TEMP_READ` or `TEMP_GET_*` when a
per-device answer is required.

### DS18B20

| Code | Command | Parameters | Response |
|------|---------|------------|----------|
| 0x20 | `TEMP_CONVERT` | `rom[8]`, or an empty payload for broadcast | `temp x 10` for an addressed device; conversion status in broadcast mode |
| 0x21 | `TEMP_READ` | `rom[8]` | `temp x 10` |
| 0x22 | `TEMP_READ_ALL` | - | `temp x 10`, one slot per cached DS18B20 |
| 0x23 | `TEMP_SET_RES` | `bits` (broadcast) or `rom[8]`, `bits` | - |
| 0x24 | `TEMP_GET_RES` | `rom[8]` | `bits` |
| 0x25 | `TEMP_SET_ALARM` | `th`, `tl` (broadcast) or `rom[8]`, `th`, `tl` | - |
| 0x26 | `TEMP_GET_ALARM` | `rom[8]` | `th`, `tl` |
| 0x27 | `TEMP_COPY` | `rom[8]` | - |
| 0x28 | `TEMP_RECALL` | `rom[8]` | - |
| 0x29 | `TEMP_DETECT_P` | `rom[8]` | `mode` |

The three scratchpad readers (`0x24`, `0x26`, `0x29`) need the same read as
`TEMP_READ`. When it fails they answer `NO_DEVICE` with an empty payload
instead of `OK` with zeros: a zero `DETECT_P` result would otherwise look like
"externally powered" and could make a host drop the strong pull-up on a
parasite bus. Each failure also increments `read_fail`.

The write-only DS18B20 commands (`TEMP_SET_RES`, `TEMP_SET_ALARM`,
`TEMP_COPY`, `TEMP_RECALL`) cannot prove that a specific addressed ROM
responded: MATCH ROM is not acknowledged by the device. They answer `OK` when
at least one device was present on the bus. `TEMP_SET_RES` additionally reports
`BUS_ERROR` when a changed resolution did not take effect, and
`TEMP_SET_ALARM`/`TEMP_COPY`/`TEMP_RECALL` report `BUS_ERROR` when the bus had
no presence at all. Use a read-back (`TEMP_GET_RES`, `TEMP_GET_ALARM`,
`TEMP_READ`) when the host must verify the addressed device.

`TEMP_READ_ALL` answers with one fixed 2-byte slot per **cached DS18B20**, in
cache order (the order in which `OW_GET_DEVICES` returns the `0x28` entries),
so its length is always `2 x` the number of DS18B20 entries in the cache. A
slot stays at `0x8000` (`BR_TEMP_INVALID` in `include/bridge.h`) when that
sensor has no valid reading: no answer or a scratchpad CRC failure. A failed
sensor therefore keeps its place instead of shifting its neighbours, and
`BR_OK` means the command completed, not that every sensor answered. Use
`TEMP_READ` with a ROM when a per-device status code is needed. Devices of
other families in the cache get no slot. Failed scratchpad reads also
increment the `read_fail` counter in `STATS_GET`. Firmware before 1.1.0
dropped failed readings instead, which shortened the array and made the
positions unreliable.

A DS18B20 powers up with **+85.0 °C** (`0x0550`) in its scratchpad. The bridge
does not keep per-device conversion history, so a read before the first
`TEMP_CONVERT` returns +85.0 as an ordinary value, indistinguishable from a
real 85.0 °C measurement. Issue a conversion before the first read when that
matters; the bridge cannot label it invalid without also rejecting genuine
85.0 °C readings.

`TEMP_SET_RES` and `TEMP_SET_ALARM` have a broadcast form: a payload of just
`bits` (1 byte) or `th, tl` (2 bytes) writes the same scratchpad values to
every DS18B20 using Skip ROM. This is how a host makes the fleet uniform
before one broadcast conversion; `owbridge_scan.py` uses it. Only the
scratchpad is written — use addressed `TEMP_COPY` per device to persist
values in EEPROM. A broadcast `TEMP_COPY` is deliberately not offered: all
devices copying to EEPROM at once would draw a large current on a
parasite-powered bus. Firmware before 1.2.0 required a ROM for both commands.

The cache itself only changes when the host asks: `OW_SEARCH`,
`OW_SEARCH_ALM` and `OW_CLEAR_CACHE` replace or empty it, and a hot-plugged
device does not appear until the next search. Between such a command and the
following `TEMP_READ_ALL` the slot order is therefore stable, so no cache
generation field is needed. Do not queue a search between `TEMP_CONVERT` and
`TEMP_READ_ALL` unless the newer device set is what you want to read.

`OW_MAX_DEVICES` sizes both the cache and the library's device table (1..32).
At the default 16 the cache holds 16 ROMs; a bus with a seventeenth device
sets `CACHE_TRUNCATED` instead of silently dropping it. Raising the option
needs RAM for 8 bytes per ROM in both tables; `OW_GET_DEVICES` still answers
20 ROMs per frame, so the host pages through offsets above that. At 32 the
UART image leaves exactly the 1 KB stack budget below the 4 KB limit; the
default 16 leaves about 1.1 KB.

### DS2431 EEPROM

| Code | Command | Parameters | Response |
|------|---------|------------|----------|
| 0x30 | `EEPROM_READ` | `rom[8]`, `addr`, `len` (1..8) | `data[len]` |
| 0x31 | `EEPROM_WRITE` | `rom[8]`, `addr`, `data[1..8]` | - |
| 0x32 | `EEPROM_READ_S` | `rom[8]` | `data[11]` |

`EEPROM_READ` rejects `addr + len > 128` and `EEPROM_WRITE` rejects a block
that is not 8-byte aligned or runs past 128 with `PARAM_ERROR`; both are
checked by the command descriptor, before the bus is touched. On a failed
read (`0x30`, `0x32`) or PIO read (`0x40`) the response is `NO_DEVICE` with an
empty payload, so the previous operation's bytes are never returned.

### DS2413 PIO

| Code | Command | Parameters | Response |
|------|---------|------------|----------|
| 0x40 | `IO_READ` | `rom[8]` | `pio`, `latches` |
| 0x41 | `IO_WRITE` | `rom[8]`, `states` | - |

### Service

| Code | Command | Parameters | Response |
|------|---------|------------|----------|
| 0x50 | `CONFIG_GET` | - | `config[40]` |
| 0x51 | `CONFIG_SET` | `config[40]` | - |
| 0x52 | `FIRMWARE_VER` | - | version string |
| 0x53 | `RESET` | - | - (the MCU reboots; the response may be lost) |
| 0x54 | `STATS_GET` | - | 9 counters (u32) + uptime |
| 0x55 | `STATS_RESET` | - | - |

`STATS_GET` returns nine big-endian u32 counters followed by uptime (seconds):
`resets`, `presence_fail`, `crc_error`, `bus_short`, `timeout`, `commands`,
`aborts`, `read_fail`, `queue_drop`. `presence_fail` counts a missing device on
`OW_RESET`; `read_fail` counts a failed device access (no answer, bad CRC, or
no presence) in the scratchpad readers, `OW_MATCH_ROM`, `OW_SKIP_ROM` and
`OW_READ_ROM`; `aborts` counts executed `OW_ABORT` commands; `queue_drop`
counts a frame dropped because both queue slots were full. `bus_short` and
`timeout` are reserved and stay 0: the board has no bus-current sensor and the
bridge has no command deadline. The host tools decode every counter by name.

### Parameter validation

Each frame is checked against a per-command descriptor before it is queued.
A malformed frame never reaches a handler and never touches the 1-Wire bus.

Payload length (`len` in the frame, excluding `cmd` and `len` itself):

| Length | Commands |
|--------|----------|
| 0 | `OW_RESET`, `OW_READ_BYTE`, `OW_READ_ROM`, `OW_GET_STATUS`, `OW_GET_COUNT`, `OW_CLEAR_CACHE`, `OW_ABORT`, `TEMP_READ_ALL`, `CONFIG_GET`, `FIRMWARE_VER`, `RESET`, `STATS_GET`, `STATS_RESET` |
| 1 | `OW_WRITE_BYTE`, `OW_READ_BYTES`, `OW_SET_PULLUP`, `OW_SET_POWER`, `TEMP_SET_RES` (broadcast `bits`) |
| 2 | `OW_GET_DEVICES`, `TEMP_SET_ALARM` (broadcast `th`, `tl`) |
| 1..32 | `OW_WRITE_BYTES`, `OW_SKIP_ROM` |
| 0..3 | `OW_SEARCH` |
| 0..1 | `OW_SEARCH_ALM` |
| 0 or 8 | `TEMP_CONVERT` (empty = broadcast, 8 = addressed) |
| 8 | `TEMP_READ`, `TEMP_GET_RES`, `TEMP_GET_ALARM`, `TEMP_COPY`, `TEMP_RECALL`, `TEMP_DETECT_P`, `EEPROM_READ_S`, `IO_READ` |
| 8..40 | `OW_MATCH_ROM` (8-byte ROM + up to 32 payload bytes) |
| 9 | `TEMP_SET_RES` (addressed), `IO_WRITE` |
| 10 | `TEMP_SET_ALARM` (addressed), `EEPROM_READ` |
| 10..17 | `EEPROM_WRITE` (ROM + address + 1..8 data bytes) |
| 40 | `CONFIG_SET` |

Argument checks applied after the length range:

- addressed commands (`OW_MATCH_ROM`, `TEMP_*`, `EEPROM_*`, `IO_*`) require a
  nonzero first ROM byte; an all-zero ROM is `PARAM_ERROR`, not a silent
  fallback to broadcast;
- `OW_READ_BYTES` accepts `n` in 1..32;
- `TEMP_SET_RES` accepts 9..12 resolution bits, in the addressed form at
  `data[8]` and in the broadcast form at `data[0]`;
- `TEMP_SET_ALARM` broadcast form needs both `th` and `tl`;
- `EEPROM_READ` accepts a length byte in 1..8 and requires
  `addr + len <= 128`;
- `EEPROM_WRITE` requires an 8-byte-aligned `addr` and `addr + n <= 128`;
- `OW_SET_PULLUP` and `OW_SET_POWER` accept 0 or 1;
- `TEMP_CONVERT` accepts an empty payload or exactly 8 bytes with a nonzero
  ROM.

Malformed frames:

- a frame shorter than two bytes (no `len` byte) cannot be parsed and is not
  answered; the previously latched response stays visible;
- an unknown command code is answered with `INVALID_CMD`;
- a wrong payload length, a truncated/padded frame, or a bad argument is
  answered with `PARAM_ERROR` (three header bytes, no data);
- the error is latched as soon as the frame is received, even while a long
  command is still running. That command's final result later replaces the
  error in the shared response slot, so a host that writes, reads and only
  then writes again never sees the overlap.

## Configuration

Stored in the last flash page (`0x08007C00`, 1 KB). The structure is 40 bytes
with the `OWBR` magic and a CRC-32. If the page is not valid, the defaults are
written.

Fields: `i2c_addr`, `uart_baud`, `timing` (stored, informational), `parasite`,
`strong_pullup`, `auto_search` (reserved), `max_devices` (reserved; the cache
size is the compile-time `OW_MAX_DEVICES`), `led_enable`.

`parasite` defaults to **1**: the strong pull-up is harmless for externally
powered devices, so the same image works on both bus types. The host can
override it at runtime with `OW_SET_POWER`.

`CONFIG_SET` validates the 40-byte block and its CRC-32, erases the page,
programs it, and reads it back before replacing the RAM copy. A flash erase or
program error (`PGERR`/`WRPRTERR`) or a failed read-back is reported as
`BUS_ERROR`; the previous RAM configuration stays active.

Fields take effect at different times:

| Field | Applied |
|-------|---------|
| `i2c_addr` | at boot, in `host_i2c_soft_init()` |
| `uart_baud` | at boot, in `host_uart_init()` |
| `parasite` | at boot, in `bridge_init()`; `OW_SET_POWER` overrides it live |
| `strong_pullup` | live, checked by `OW_SET_PULLUP` |
| `led_enable` | live, checked on every LED update |
| `timing` | stored only, informational |
| `auto_search`, `max_devices` | reserved; the cache size is compile-time `OW_MAX_DEVICES` |

Changing `i2c_addr` or `uart_baud` therefore needs a reboot before the new
transport settings are used; the `CONFIG_SET` response itself is sent with the
old ones.

## Resource usage

| Variant | Flash (`-O2`) | RAM (bss + data) |
|---------|---------------|------------------|
| UART | 23 732 B | 2 936 B |
| SPI | 20 292 B | 2 212 B |
| I2C | 20 052 B | 2 068 B |

All fit the 31 KB code region and the 4 KB RAM. The RAM figures exclude the
stack: UART leaves about 1.1 KB below the 4 KB limit after its 512-byte RX
ring, SPI and I2C leave about 1.8-2.0 KB. The linker script defines
`_Min_Stack_Size` as a budget but does not enforce it.

The per-command descriptor still occupies 12 bytes, so adding `min_len`,
`max_len` and `flags` did not grow the 256-entry `cmd_map` (3072 bytes in
`.rodata`); the validation code itself adds about 80 bytes.

The library keeps `OW_OPT` (`-O2`), while the firmware adds `-flto`,
`-ffunction-sections/-fdata-sections` and
`-fno-tree-loop-distribute-patterns`. The last one matters: without it GCC
turns the explicit 32-bit copy loops in `fast_copy()` back into calls to the
byte-wise libc `memcpy`. A firmware-only `-O3` build also fits (about 28.8 KB)
but made the instant command path slower on the Cortex-M0, so `-O2` is kept.
`-Os` shrinks the image further if flash ever becomes tight; the 256-entry
command map and the inlined copies are a deliberate flash-for-speed trade.

## Hardware test results

Verified on a bench with a 1-Wire bus carrying 7 x DS18B20, 1 x DS2431 and
1 x DS2413, parasite-powered, flashed through an ST-Link V2.

| Test | Result |
|------|--------|
| `OW_RESET` | presence = 1 |
| `OW_SEARCH` | 9 devices |
| `OW_GET_DEVICES` | 7 x 0x28, 1 x 0x2D, 1 x 0x3A |
| `TEMP_CONVERT` (broadcast) | OK |
| `TEMP_READ_ALL` | 27.0 .. 27.5 C on all 7 sensors |
| raw scratchpad | temp 0x01B0 (27 C), cfg 0x7F (12 bit), CRC valid |
| DS2431 read memory / scratchpad | OK |
| DS2413 PIO write/read | OK |
| `CONFIG_GET` / `STATS_GET` | 40 / 40 bytes |
| AT commands (UART build) | all eight; `AT+TEMP` takes about 1 s |

The UART build was exercised end to end. The I2C build was exercised end to
end through a CH341A USB-I2C master at 100 kHz (address `0x30`) with a logic
analyzer: `FIRMWARE_VER`, `OW_RESET`, `OW_SEARCH`, `OW_GET_COUNT`,
`OW_GET_DEVICES`, `OW_GET_STATUS`, `STATS_GET` and `TEMP_READ_ALL` all return
well-formed frames, and the analyzer decodes the write/read transactions and
every ACK. The CH341A's ~15 us write-to-read turnaround now works without any
host-side gap for the instant commands. 400 kHz was tried and is not supported
by the polled slave; 100 kHz is the validated rate. The SPI build compiles and
fits; its protocol test still needs an external SPI master.

An 18-minute I2C load test (77 286 bulk 163-byte reads, 202 777 transactions,
zero errors and zero resets) is documented in
[`docs/i2c-stress-test.md`](docs/i2c-stress-test.md). A 60-minute torture run
(252 646 bulk reads, 776 677 transactions, 42.0 MB read) adds malformed-frame
bursts, stale-buffer replay, queue/abort churn and parser fuzz; it also
finished with zero errors, zero resets and zero bad responses, documented in
[`docs/i2c-torture-test.md`](docs/i2c-torture-test.md).

The host demo surfaced two firmware issues that are now fixed. The DS18B20
driver parks in parasite mode with the strong pull-up engaged, which on this
port switches PA10 to push-pull and broke any following search; `bridge.c` now
restores the open-drain line before every command unless `OW_SET_PULLUP` asked
to hold it. `stats_uptime()` also only advanced while the I2C bus was busy for
more than 50 ms; the main loop now calls `board_millis()` unconditionally so
the counter follows real time while the bus is idle.

## Host demo

[`tools/owbridge_demo.py`](tools/owbridge_demo.py) is a stdlib-only Python demo
for the I2C build. It drives the bridge through a CH341A USB-I2C adapter and
walks through every capability: search, DS18B20 temperature, DS2431 EEPROM,
DS2413 PIO, configuration, statistics, queueing, abort, latency and a stress
load. Every scenario also returns a dictionary, so `--json` makes it
scriptable; `--verbose` prints every I2C frame.

```text
python owbridge_demo.py scan
python owbridge_demo.py temp
python owbridge_demo.py eeprom --dump
python owbridge_demo.py timing --all
python owbridge_demo.py selftest
```

Captured output from the 9-device bench, the transport behaviour and the quirks
the demo uncovered are in [`docs/demo.md`](docs/demo.md).

[`tools/protocol_test.py`](tools/protocol_test.py) reuses the same transport for
protocol conformance. It sends every command at its minimum, maximum and
out-of-range payload lengths, checks the semantic argument rules, replays stale
buffer contents, exercises the transport directly (partial and over-long
reads, truncated headers, foreign addresses), and can fuzz the parser:

```text
python protocol_test.py
python protocol_test.py --fuzz 10000
python protocol_test.py --destructive
```

The randomized host-link fuzzing session and its coverage are summarized in
[`docs/i2c-fuzz.md`](docs/i2c-fuzz.md).

[`tools/owbridge_scan.py`](tools/owbridge_scan.py) is the host side of the
library's `4_scan_mode` example: one broadcast resolution write, then a
broadcast Convert T and a `TEMP_READ_ALL` every `--interval` seconds. It prints
the NACK and poll counts of both commands per cycle plus a summary, which shows
what a normal measurement cadence actually costs on the service window:

```text
python owbridge_scan.py
python owbridge_scan.py --poll-gap 250
python owbridge_scan.py --speed 20k --cycles 50 --json
```

On the 9-device bench at 100 kHz, 20 cycles of 12-bit scan mode measured 149
NACKs per cycle with back-to-back polls and 91 with `--poll-gap 250`, about 7%
of the BUSY polls in both cases; at 20 kHz the same run measured zero.

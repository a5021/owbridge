# owbridge - a USART/SPI/soft-I2C to 1-Wire bridge on the STM32F030F4P6

Firmware for a microcontroller gateway that lets a host drive a 1-Wire bus.
Every microsecond-scale 1-Wire timing is generated by TIM1 and DMA through the
[`stm32-async-1wire`](https://github.com/a5021/stm32-async-1wire) library
(v3.1.2); the CPU only polls completion flags. **The firmware is fully polled:
no NVIC interrupts are enabled.**

New to the protocol? [`docs/how-it-works.md`](docs/how-it-works.md) is an
illustrated tour with captured frames, a queued command, a raw DS18B20
conversation and an hour of load-test output.

## Host interface selection

The host-facing interface is chosen at compile time, one per firmware image:

```bash
cmake -DHOST_IF=UART ...   # USART1
cmake -DHOST_IF=SPI  ...   # SPI1 slave
cmake -DHOST_IF=I2C  ...   # software I2C slave
```

Only the selected `host_*.c` is compiled, so flash and RAM stay small and the
main loop only services one host interface plus the 1-Wire bus.

## Hardware platform

STM32F030F4P6 in a TSSOP-20 package. The datasheet documents 16 KB of flash,
but the die carries **32 KB** (like the F6P6); the upper 16 KB are used by the
linker script. RAM is 4 KB.

Pins common to every variant:

| Pin | Function | Notes |
|-----|----------|-------|
| PA10 | 1-Wire DQ | TIM1_CH3, AF2, open-drain (owned by the library) |
| PA9 | Strong pull-up switch | gate-driver input, active-high, push-pull |
| PA0 / PA1 | Status / error LED | push-pull |
| PB1 / PF0 | Config jumpers 0 / 1 | input with pull-up |
| PF1 | Spare | input with pull-up |
| PA13/PA14 | SWD | programming |

Host-interface pins:

| Variant | Pins |
|---------|------|
| UART | PA2 = USART1 TX, PA3 = USART1 RX |
| SPI | PA4 = NSS (GPIO CS), PA5 = SCK, PA6 = MISO, PA7 = MOSI |
| I2C | PA4 = SCL (input, pull-up), PA5 = SDA (open-drain) |

1-Wire power: 3.3 V with a 4.7 kOhm pull-up (externally powered devices) or
2.2 kOhm (parasite power, with PA9 driving the strong-pull-up switch, e.g. a
P-MOSFET through its gate driver).

## Building

```bash
cmake -S . -B build \
    -DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi-gcc.cmake \
    -DHOST_IF=UART
cmake --build build -j
```

The first configure fetches `stm32-async-1wire` v3.1.2 and the pinned CMSIS
repositories from GitHub into `build/_deps/`. No dependencies are vendored in
the repository.

Output: `build/owbridge.elf`, `build/owbridge.bin`, `build/owbridge.hex`.

Flashing:

```bash
st-flash write build/owbridge.bin 0x08000000
# or
openocd -f interface/stlink.cfg -f target/stm32f0x.cfg \
    -c "program build/owbridge.elf verify reset exit"
```

## Transport details

- **UART**: TX via DMA1 channel 2, RX via DMA1 channel 5 in circular mode
  (remapped from the default channel 3, which the 1-Wire feed owns, through
  `SYSCFG_CFGR1.USART1RX_DMA_RMP`). The main loop polls the DMA state.
- **SPI**: polled RXNE/TXE in the main loop. DMA is not possible: SPI1_RX is
  DMA1 channel 2 and SPI1_TX is DMA1 channel 3, which the 1-Wire engine owns.
- **I2C**: software slave, polled SCL/SDA edges in the main loop. No EXTI, no
  DMA (GPIO edges cannot trigger DMA). During an I2C transaction the 1-Wire
  poll is deferred (with a 50 ms no-edge safety valve), so its encode/decode
  cannot drop SCL edges at 100 kHz; the 1-Wire timing is hardware-generated, so
  only the state machine is delayed. A read transfers the response straight from
  the bridge's latched buffer; there is no `memcpy` in the SCL edge handler,
  because a copy of up to 163 bytes would outlast the 5 us low phase of a
  100 kHz clock. The dispatcher is a 256-entry table indexed by the command
  byte, commands are copied straight into the bus slot, and the hot copies are
  inline 32-bit moves (`fast_copy()`), not the byte-wise libc `memcpy`.

### I2C timing margin

The poll rate was measured with the one-off TIM3 profiler
(`-DOWBRIDGE_PROFILE=ON`, results read over SWD) on the 9-device bench, I2C
build at `-O2`:

| Metric | min | max | average |
|--------|-----|-----|---------|
| `host_i2c_soft_poll()` | 0 us | 1 us | 0.90 us |
| `bridge_poll()` | 1 us | 2 us | 1.17 us |
| main loop | 4 us | 5 us | 4.09 us |

These numbers include the profiler's two TIM3 reads and volatile bookkeeping
(about 1.5-2 us per iteration); the production loop is therefore about 2-3 us.
While an I2C transaction is active `bridge_poll()` is skipped, so the busy
loop is shorter still. The SCL half-period at 100 kHz is 5 us, so 100 kHz has
margin; 400 kHz (1.25 us) does not.

**The 1-2 us `bridge_poll()` figure is the idle case.** While a long command
is running, the first `bridge_poll()` after STOP executes one library event,
which is much heavier. The library's CPU profile (`stm32-async-1wire` v3.1.2,
F030 at 8 MHz) reports a worst driver work event of 2 857 cycles (59.5 us at
48 MHz) and a worst public poll of 7 217 cycles (150 us at 48 MHz). The latter
includes the example's completion callback; this firmware's callback is much
lighter, but until the extended profiler is read on the bench the honest design
bound is the public-poll figure plus flash wait states: **roughly 160-210 us**
for the measurement path and **70-100 us** for search. During that window the
slave is not sampling SCL, so a START/clock burst that arrives earlier can be
missed. This is the mechanism behind the NACKs on `TEMP_READ_ALL` and
`OW_SEARCH` in the torture test, not necessarily an adapter defect.

Host contract while a long command is `BUSY`: either leave at least **250 us**
after STOP before the next START (a conservative value covering the bound
above; the profiler will replace it with the measured worst case), or keep the
current behaviour and treat a NACK or an all-`FF` read as "not ready", then
retry. The demo and the torture harness do the latter. Instant commands are
unaffected: they finish inside the STOP handler.

The 50 ms safety valve now requires **no SCL/SDA edges for 50 ms**, not merely
a transaction longer than 50 ms. A 163-byte frame at 20 kHz lasts about 74 ms
but keeps clocking, so it is never interrupted; the valve only releases a
wedged or held bus. 100 kHz remains the validated rate.

`CONFIG_SET` is the one command that blocks the sampler by design: page erase
and programming run inside a single `bridge_poll()` and take tens of
milliseconds. The host must therefore retry (`NACK` / `FF FF`) across it; the
demo's 10 s timeout covers this. The profiler records the actual duration in
`prof_config_set_us`.

### I2C host turnaround

The STOP handler is short enough to survive the CH341A's ~15 us
STOP-to-START turnaround for instant commands: version, cached queries,
config and stats are completed inside `bridge_submit()` before the handler
returns, so the read that follows immediately sees the final response. Long
1-Wire commands start their engine at STOP and latch `BUSY`; the first
main-loop poll after STOP completes one step and can outlast the 15 us
turnaround, so a chained read address may be NACKed and must be retried (see
the timing margin above). Once the host is polling, the response arrives as
usual.

Measured worst case for an instant command on the 9-device bench: about 10 us
from STOP detection to the latched response. No host-side gap is required:
`gap = 0` on the CH341A works for `FIRMWARE_VER`, `OW_GET_COUNT`,
`OW_GET_STATUS`, `OW_GET_DEVICES` (with a populated cache), `STATS_GET` and
`CONFIG_GET`. Details: [`docs/i2c-timing.md`](docs/i2c-timing.md).

## Protocol

### Binary frame (UART and SPI)

```
Command:  AA 55 [cmd][len][data...] [crc8]      (UART)
          5A A5 [status][cmd][len][data...] [crc8] (response)
```

The SPI transport uses the same `[cmd][len][data...]` /
`[status][cmd][len][data...]` frame without the `AA 55` / `5A A5` header,
inside two CS-framed phases:

1. CS low: the master sends `[cmd][len][data...]`.
2. CS high: the bridge starts the command.
3. CS low: the master clocks dummy bytes; the slave returns
   `[status][cmd][len][data...]`.

The software I2C slave uses the same bare frame: a write transaction delivers
`[cmd][len][data...]`, a read transaction returns
`[status][cmd][len][data...]`.

`crc8` is the Dallas/Maxim CRC-8 (polynomial 0x8C).

### Transport integrity

Only UART frames carry a checksum. The SPI and software-I2C frames have none:
they rely on CS / START-STOP framing, the 7-bit address ACK (I2C only), and the
per-command length and argument checks in the `br_cmd_desc_t` table.

| Transport | Framing | Wire checksum | Undetected by the transport |
|-----------|---------|---------------|-----------------------------|
| UART | `AA 55` header, length | CRC-8 over `cmd`..`data` (both directions) | only patterns beyond CRC-8 (all single-bit and bursts <= 8 bits are caught) |
| SPI | two CS-framed phases | none | any bit flip that keeps the length plausible |
| I2C | START/STOP, 7-bit address + ACK | none | any bit flip that keeps the length plausible |

Commands whose payload carries its own end-to-end check are still protected on
SPI/I2C: a ROM is checked with the Dallas CRC-8, a DS2431 scratchpad read with
CRC-16, and a configuration block with CRC-32. A corrupted length, unknown
command or invalid argument is rejected with `PARAM_ERROR` / `INVALID_CMD`.
For transport-level integrity on SPI/I2C, wrap the frame in an application
checksum; adding CRC-8 to those frames would be a protocol v2 change.

### Destructive commands

Both commands that can leave the device in a bad state verify the complete
payload before the irreversible step:

- **`CONFIG_SET`** (0x51) checks the `OWBR` magic, the version, every field
  range and the CRC-32 over the first 36 bytes *before* the flash page is
  erased. A checksum mismatch returns `CRC_ERROR`; a bad header or field
  returns `PARAM_ERROR`. The page is never written with a corrupted
  `i2c_addr`, so the I2C build cannot be bricked by a bad frame. Previously
  the firmware recomputed the CRC instead of checking it.
- **`EEPROM_WRITE`** (0x31) uses the DS2431 driver's verification: the
  scratchpad CRC-16, the TA/ES echo, the PF bit and the read-back payload are
  all checked. A failure aborts **before** Copy Scratchpad, returning
  `CRC_ERROR` (a Write Scratchpad failure returns `BUS_ERROR`), so corrupted
  data is never programmed. A rejected write leaves the page unchanged.

### Status codes

| Code | Name | Meaning |
|------|------|---------|
| 0x00 | OK | success |
| 0x01 | BUSY | command in progress; poll again |
| 0x02 | NO_DEVICE | no presence pulse |
| 0x03 | CRC_ERROR | checksum mismatch |
| 0x04 | BUS_SHORT | bus short circuit |
| 0x05 | TIMEOUT | operation timed out |
| 0x06 | INVALID_CMD | unknown command |
| 0x07 | PARAM_ERROR | invalid parameters (payload length or argument) |
| 0x08 | BUS_ERROR | generic bus failure |

Asynchronous commands (search, conversion, EEPROM write) first return `BUSY`;
the host keeps polling the response until it becomes `OK` or an error.

| 0x04 | `OW_WRITE_BYTES` | `data[1..32]` | - |
| 0x05 | `OW_READ_BYTES` | `n` (data[0], 1..32) | `data[n]` |

| 0x07 | `OW_SKIP_ROM` | payload (1..32) | - |

### Parameter validation

Each frame is checked against a per-command descriptor before it is queued.
A malformed frame never reaches a handler and never touches the 1-Wire bus.

Payload length (`len` in the frame, excluding `cmd` and `len` itself):

| Length | Commands |
|--------|----------|
| 0 | `OW_RESET`, `OW_READ_BYTE`, `OW_READ_ROM`, `OW_GET_STATUS`, `OW_GET_COUNT`, `OW_CLEAR_CACHE`, `OW_ABORT`, `TEMP_READ_ALL`, `CONFIG_GET`, `FIRMWARE_VER`, `RESET`, `STATS_GET`, `STATS_RESET` |
| 1 | `OW_WRITE_BYTE`, `OW_READ_BYTES`, `OW_SET_PULLUP`, `OW_SET_POWER` |
| 2 | `OW_GET_DEVICES` |
| 1..32 | `OW_WRITE_BYTES`, `OW_SKIP_ROM` |
| 0..3 | `OW_SEARCH` |
| 0..1 | `OW_SEARCH_ALM` |
| 0 or 8 | `TEMP_CONVERT` (empty = broadcast, 8 = addressed) |
| 8 | `TEMP_READ`, `TEMP_GET_RES`, `TEMP_GET_ALARM`, `TEMP_COPY`, `TEMP_RECALL`, `TEMP_DETECT_P`, `EEPROM_READ_S`, `IO_READ` |
| 8..40 | `OW_MATCH_ROM` (8-byte ROM + up to 32 payload bytes) |
| 9 | `TEMP_SET_RES`, `IO_WRITE` |
| 10 | `TEMP_SET_ALARM`, `EEPROM_READ` |
| 10..17 | `EEPROM_WRITE` (ROM + address + 1..8 data bytes) |
| 40 | `CONFIG_SET` |

Argument checks applied after the length range:

- addressed commands (`OW_MATCH_ROM`, `TEMP_*`, `EEPROM_*`, `IO_*`) require a
  nonzero first ROM byte; an all-zero ROM is `PARAM_ERROR`, not a silent
  fallback to broadcast;
- `OW_READ_BYTES` accepts `n` in 1..32;
- `TEMP_SET_RES` accepts 9..12 resolution bits;
- `EEPROM_READ` accepts a length byte in 1..8;
- `OW_SET_PULLUP` and `OW_SET_POWER` accept 0 or 1;
- `TEMP_CONVERT` accepts an empty payload or exactly 8 bytes with a nonzero
  ROM.

Malformed frames:

- a frame shorter than two bytes (no `len` byte) cannot be parsed and is not
  answered; the previously latched response stays visible;
- an unknown command code is answered with `INVALID_CMD`;
- a wrong payload length, a truncated/padded frame, or a bad argument is
  answered with `PARAM_ERROR` (three header bytes, no data);
- the error is latched as soon as the frame is received, even while a long
  command is still running. That command's final result later replaces the
  error in the shared response slot, so a host that writes, reads and only
  then writes again never sees the overlap.

## Configuration

Stored in the last flash page (`0x08007C00`, 1 KB). The structure is 40 bytes
with the `OWBR` magic and a CRC-32. If the page is not valid, the defaults are
written.

Fields: `i2c_addr`, `uart_baud`, `timing` (stored, informational), `parasite`,
`strong_pullup`, `auto_search` (reserved), `max_devices` (reserved; the cache
size is the compile-time `OW_MAX_DEVICES`), `led_enable`.

`parasite` defaults to **1**: the strong pull-up is harmless for externally
powered devices, so the same image works on both bus types. The host can
override it at runtime with `OW_SET_POWER`.

## Resource usage

| Variant | Flash (`-O2`) | RAM (bss + data) |
|---------|---------------|------------------|
| UART | 25 124 B | 2 416 B |
| SPI | 21 704 B | 2 196 B |
| I2C | 21 812 B | 2 044 B |

All fit the 31 KB code region and the 4 KB RAM. The RAM figures exclude the
stack; about 1.6-2.0 KB remains below the 4 KB limit. The linker script
defines `_Min_Stack_Size` as a budget but does not enforce it.

The per-command descriptor still occupies 12 bytes, so adding `min_len`,
`max_len` and `flags` did not grow the 256-entry `cmd_map` (3072 bytes in
`.rodata`); the validation code itself adds about 80 bytes.

The library keeps `OW_OPT` (`-O2`), while the firmware adds `-flto`,
`-ffunction-sections/-fdata-sections` and
`-fno-tree-loop-distribute-patterns`. The last one matters: without it GCC
turns the explicit 32-bit copy loops in `fast_copy()` back into calls to the
byte-wise libc `memcpy`. A firmware-only `-O3` build also fits (about 28.8 KB)
but made the instant command path slower on the Cortex-M0, so `-O2` is kept.
`-Os` shrinks the image further if flash ever becomes tight; the 256-entry
command map and the inlined copies are a deliberate flash-for-speed trade.

## Hardware test results

Verified on a bench with a 1-Wire bus carrying 7 x DS18B20, 1 x DS2431 and
1 x DS2413, parasite-powered, flashed through an ST-Link V2.

| Test | Result |
|------|--------|
| `OW_RESET` | presence = 1 |
| `OW_SEARCH` | 9 devices |
| `OW_GET_DEVICES` | 7 x 0x28, 1 x 0x2D, 1 x 0x3A |
| `TEMP_CONVERT` (broadcast) | OK |
| `TEMP_READ_ALL` | 27.0 .. 27.5 C on all 7 sensors |
| raw scratchpad | temp 0x01B0 (27 C), cfg 0x7F (12 bit), CRC valid |
| DS2431 read memory / scratchpad | OK |
| DS2413 PIO write/read | OK |
| `CONFIG_GET` / `STATS_GET` | 40 / 32 bytes |
| AT commands (UART build) | all eight; `AT+TEMP` takes about 1 s |

The UART build was exercised end to end. The I2C build was exercised end to
end through a CH341A USB-I2C master at 100 kHz (address `0x30`) with a logic
analyzer: `FIRMWARE_VER`, `OW_RESET`, `OW_SEARCH`, `OW_GET_COUNT`,
`OW_GET_DEVICES`, `OW_GET_STATUS`, `STATS_GET` and `TEMP_READ_ALL` all return
well-formed frames, and the analyzer decodes the write/read transactions and
every ACK. The CH341A's ~15 us write-to-read turnaround now works without any
host-side gap for the instant commands. 400 kHz was tried and is not supported
by the polled slave; 100 kHz is the validated rate. The SPI build compiles and
fits; its protocol test still needs an external SPI master.

An 18-minute I2C load test (77 286 bulk 163-byte reads, 202 777 transactions,
zero errors and zero resets) is documented in
[`docs/i2c-stress-test.md`](docs/i2c-stress-test.md). A 60-minute torture run
(252 646 bulk reads, 776 677 transactions, 42.0 MB read) adds malformed-frame
bursts, stale-buffer replay, queue/abort churn and parser fuzz; it also
finished with zero errors, zero resets and zero bad responses, documented in
[`docs/i2c-torture-test.md`](docs/i2c-torture-test.md).

The host demo surfaced two firmware issues that are now fixed. The DS18B20
driver parks in parasite mode with the strong pull-up engaged, which on this
port switches PA10 to push-pull and broke any following search; `bridge.c` now
restores the open-drain line before every command unless `OW_SET_PULLUP` asked
to hold it. `stats_uptime()` also only advanced while the I2C bus was busy for
more than 50 ms; the main loop now calls `board_millis()` unconditionally so
the counter follows real time while the bus is idle.

## Host demo

[`tools/owbridge_demo.py`](tools/owbridge_demo.py) is a stdlib-only Python demo
for the I2C build. It drives the bridge through a CH341A USB-I2C adapter and
walks through every capability: search, DS18B20 temperature, DS2431 EEPROM,
DS2413 PIO, configuration, statistics, queueing, abort, latency and a stress
load. Every scenario also returns a dictionary, so `--json` makes it
scriptable; `--verbose` prints every I2C frame.

```text
python owbridge_demo.py scan
python owbridge_demo.py temp
python owbridge_demo.py eeprom --dump
python owbridge_demo.py timing --all
python owbridge_demo.py selftest
```

Captured output from the 9-device bench, the transport behaviour and the quirks
the demo uncovered are in [`docs/demo.md`](docs/demo.md).

[`tools/protocol_test.py`](tools/protocol_test.py) reuses the same transport for
protocol conformance. It sends every command at its minimum, maximum and
out-of-range payload lengths, checks the semantic argument rules, replays stale
buffer contents, and can fuzz the parser:

```text
python protocol_test.py
python protocol_test.py --fuzz 10000
python protocol_test.py --destructive
```
